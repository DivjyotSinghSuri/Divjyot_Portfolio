About Me

DS
Delhi NCR, India 🇮🇳

I build data systems — not just scripts. Every project I ship follows the same discipline: define the grain first, enforce schema at ingestion, validate before compute, and design the model so analysts don't have to guess what a metric means. That means surrogate keys, grain-level contracts, and fact tables that don't silently break when source data changes.

I prefer ELT over ETL because transformations belong in the warehouse, not hidden inside ingestion jobs. I use Databricks for orchestrated, multi-layer pipelines and AWS (Lambda + Glue + S3 + Athena) for event-driven serverless architectures. I don't treat these as interchangeable — I pick the stack that fits the data volume, latency requirement, and downstream use case.

Currently in B.Tech (Information Technology) at ABES Engineering College, Ghaziabad — graduating June 2027. Everything in this portfolio was built independently, outside coursework, against real datasets.

01

FMCG ELT Pipeline — Databricks Medallion Architecture

December 2025

Problem: Raw FMCG sales data in S3 had no consistent schema, duplicate records, and no agreed metric definitions — making downstream reporting unreliable. Approach: Built a 3-layer ELT pipeline in Databricks (Bronze ingestion → Silver cleansing → Gold star schema). Defined grain-level contracts for each fact table; enforced null, duplicate, and date-format checks at each layer boundary. Automated daily scheduling with CloudWatch-style failure alerting. Outcome: Eliminated metric ambiguity across 4+ reporting use cases; cut analyst query-prep time by ~35% and manual monitoring by 3 hrs/week.

02

AWS Serverless Orders Data Lake

2025

Problem: Corrupt or incomplete CSV order files were reaching the ETL layer, wasting Glue compute and contaminating the curated dataset. Approach: Designed a validate-before-compute architecture: Lambda rejects empty or malformed files at S3 upload, passing only clean data to Glue Visual ETL, which writes partitioned Parquet to a curated layer queryable via Athena. CloudWatch alarms + SNS email ensure no silent failures. Outcome: Zero downstream contamination from bad source files; Athena scan costs reduced via partition pruning on order_date.

EIA Energy API → S3 Medallion Pipeline

2025

05

Logistics Fulfillment Dimensional Model

February 2026

Problem: Source data was a one-big-table (OBT) flat structure — no defined grain, no separation of concerns, joins exploded row counts unpredictably. Approach: Decomposed OBT into a normalised star schema with grain defined as one row per line-item per order. Built surrogate-key-based dimension tables (customer, product, date, carrier) and a procedural fact table tracking the full fulfillment lifecycle. Validated with analytical SQL — join integrity checks, aggregation accuracy tests, and metric behavior across all stages. Outcome: ~30% query efficiency gain; model is fully documented with LucidChart diagrams and grain contracts.

↑ 30% query efficiency · Grain: 1 row per line-item per order · Full lifecycle
